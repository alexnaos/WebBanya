# Предложения по оптимизации проекта WebBanya3

## 🔴 Критические проблемы (необходимо исправить)

### 1. Дублирование объектов и `--allow-multiple-definition`

**Проблема:** Объекты `OneWire`, `DallasTemperature`, `Adafruit_SSD1306 display` объявлены одновременно в `sensors.cpp` и `lib/work.cpp`. Компилятор даёт ошибку множественного определения, которая подавляется флагом `--allow-multiple-definition` в `platformio.ini`. Это **опасный костыль**: линковщик берёт первое попавшееся определение, что может привести к непредсказуемому поведению.

**Решение:**
- Удалить `lib/work.cpp` из сборки (переместить в `archive/` или удалить)
- Либо вынести объекты в отдельный файл с `extern`-объявлениями
- Убрать флаг `-Wl,--allow-multiple-definition` из `build_flags`

### 2. Дублирование enum `kk` и адресов датчиков

**Проблема:** enum `kk` определён в `config.h` и повторно в `lib/work.cpp`. Адреса `addr1`, `addr2` также продублированы. При использовании `lib/work.cpp` значения могут расходиться.

**Решение:** Один источник правды — `config.h`. Удалить дубликаты из `work.cpp` или удалить сам файл.

### 3. lib/work.cpp не должен быть в lib/

**Проблема:** Файлы в `lib/` автоматически линкуются PlatformIO в каждый исходный файл. `lib/work.cpp` — это копия основной прошивки, а не библиотека. Он грузится в каждый `.cpp`, создавая множественные определения.

**Решение:** Переместить в `archive/` или удалить.

## 🟡 Серьёзные проблемы

### 4. Хаотичная структура проекта

**Проблема:** Логика раскидана по файлам с пересекающимися зонами ответственности:
- `config.h` содержит не только конфигурацию, но и глобальные переменные (`tmr`), extern-объявления и объявления функций
- `sensors.cpp` содержит и датчики, и OLED, и функции обновления дисплея
- `main.cpp` содержит MQTT, WiFi, ШИМ и часть инициализации
- `lib/work.cpp` — дублирующийся черновик

**Решение:** Рефакторинг по модулям:
```
src/
├── main.cpp           # Только setup/loop
├── config.h           # Только defines, extern-объявления
├── sensors.cpp/.h     # Датчики DS18B20
├── display.cpp/.h     # OLED дисплей
├── mqtt.cpp/.h        # MQTT клиент
├── wifi.cpp/.h        # Wi-Fi менеджер
├── control.cpp/.h     # ШИМ управление нагрузкой
├── automation.cpp/.h  # Сценарии JSON
├── rtc.cpp/.h         # DS3231 часы
└── ui_portal.cpp/.h   # Веб-интерфейс
```

### 5. `setStampZone(3)` вызывается трижды

**Проблема:** В `main.cpp` строка 81 и 103, и 137 — одни и те же вызовы:

```cpp
setStampZone(3); // main.cpp строки 81, 103, 137
```

Бесполезные повторные вызовы. Оставить один в `setup()` после всего.

### 6. `WiFi.mode(WIFI_STA)` установлен после `wifiMulti.addAP()`

**Проблема:** В `main.cpp` строки 116-120 сначала добавляются AP, потом устанавливается режим. Правильнее — сначала установить режим, потом добавлять точки.

### 7. Блокирующий цикл ожидания WiFi

**Проблема:** В `main.cpp` строка 126-130:

```cpp
while (wifiMulti.run() != WL_CONNECTED) {
    delay(500);
}
```

Если WiFi недоступен — ESP зависает на неопределённое время. Лучше сделать таймаут и работать офлайн.

## 🟠 Средней важности

### 8. Миллис переполнение через 50 дней

**Проблема:** `uint32_t millis()` переполняется через ~50 дней. Все таймеры вида:

```cpp
if (millis() - tmr >= interval) { tmr = millis(); ... }
```

корректно обрабатывают переполнение благодаря беззнаковой арифметике, но статические переменные `tmr` сбрасываются на 0, из-за чего после переполнения будет двойной вызов. Рекомендуется использовать `millis()` с проверкой `if (current - tmr >= interval)` — это уже сделано, ок. Но:
- `tmr_mqtt_send` и `tmrControl` объявлены статическими внутри `if` блоков — при переполнении будет задержка на interval
- Решение: ничего срочного, но стоит иметь в виду

### 9. MQTT reconnect каждые 5 мс проверяется

**Проблема:** В `mqttReconnect()`:

```cpp
if (millis() % 5000 != 0) return; // Проверка раз в 5 секунд
```

Но `mqttReconnect()` вызывается из `loop()` → `mqttReconnect()` вызывается снова. Из-за того, что в `loop()` условие `if (WiFi.status() == WL_CONNECTED)`, она не вызывается, если WiFi отвалился. Но при обрыве WiFi reconnect не будет пытаться подключиться — он завязан на WiFI-статус. Правильнее: отделить MQTT-reconnect от WiFi и добавить таймаут.

### 10. Неиспользуемые переменные в enum

**Проблема:** В `kk` объявлены `lbl1`, `lbl2`, `btn1`, `btn2`, `txt`, `pass`, `uintw`, `intw`, `int64w`, `color`, `sldmin`, `sldmax`, `date`, `timew`, `datime` — часть из них не используется в конечной сборке (в `ui_portal.cpp` и `main.cpp`). Это тратит место в базе данных.

**Решение:** Оставить только используемые ключи: `txt`, `toggle`, `slider`, `selectw`, `tmp1`, `tmp2`, `logic`, `date`, `timew`, `datime`, `lbl1`, `lbl2`.

### 11. `GyverOLED` в зависимостях, но не используется

**Проблема:** В `platformio.ini` указан `gyverlibs/GyverOLED@^1.6.4`, но в коде используется `Adafruit SSD1306`. `GyverOLED` не нужен.

## 🟢 Косметические улучшения

### 12. Отсутствует обработка ошибок датчиков

**Проблема:** `sensors.getTempCByIndex(0)` может вернуть `DEVICE_DISCONNECTED_C` (-127°C), но по коду это значение записывается в БД. На OLED отображается "--", но в БД и MQTT уходит мусорное значение.

**Решение:** Проверять на `DEVICE_DISCONNECTED_C` перед записью в БД.

### 13. Магические числа

**Проблема:** В коде разбросаны числа: `200` (logger), `1023` (PWM max), `100` (таймеры), `2000` (MQTT send), `500` (OLED refresh). Стоит вынести в `#define` или `constexpr` в `config.h`.

### 14. Отсутствие watchdog

На ESP8266 стоит включить Software Watchdog (`ESP.wdtEnable()`) или использовать `ESP.wdtFeed()` в `loop()`, так как `delay()` в цикле ожидания WiFi может привести к сбросу.

### 15. Отсутствие OTA-обновлений

Можно добавить `ArduinoOTA` для беспроводных обновлений прошивки.

### 16. Нет тестов и CI

`test/` пуст. Можно добавить юнит-тесты для бизнес-логики (сценарии, управление). И `.github/workflows/` для автоматической сборки.
